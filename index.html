1. What "Linux" actually means

"Linux" is, strictly, one thing: the kernel — a single program that starts running the moment your device's bootloader hands it control, and never stops until you power off. It talks directly to the CPU and hardware, and its job is to referee everything: which process gets the CPU next, how physical memory is divided up, how files are read from storage, how network packets move, which process is allowed to talk to which device.

Everything you'd normally call "a Linux system" — a shell prompt, ls, a package manager, systemd, Python, a desktop — is userspace: ordinary programs running on top of the kernel, using it through a fixed set of system calls (open(), read(), fork(), ...). None of that is "Linux" in the strict sense; it's software that a distribution (Ubuntu, Debian, Alpine, Android, and — by the end of this project — our own) bundles on top of the Linux kernel.

That separation is exactly why Yocto exists and why this project is possible at all: the kernel is one replaceable component, and a "distro" is really just a chosen combination of kernel + C library + init system + package set. Yocto lets us pick every one of those deliberately, instead of inheriting a desktop distro's defaults on a device with 4GB of storage and no monitor.

2. What happens when any computer boots

Before Linux is running anything, several handoffs happen, each one loading and trusting the next:

firmware
→
bootloader
→
kernel + device tree
→
rootfs mounted
→
init (PID 1)
→
userspace
  • Firmware — the first code that runs, baked into the chip itself (UEFI/BIOS on a PC; a mask ROM on an embedded SoC). It knows nothing about your OS; its only job is to bring up just enough hardware (RAM, storage) to find and load the next stage.
  • Bootloader — a small program (GRUB on a PC; U-Boot or NVIDIA's CBoot on embedded boards) that can read a filesystem, find a kernel image, load it into RAM, and jump to it. This is the layer we configure for the TX2.
  • Kernel + device tree — the kernel starts running, but on embedded hardware it doesn't yet know what's actually wired to the chip. A PC can ask its firmware ("ACPI tables") what hardware exists; an SoC board usually can't self-describe, so the bootloader also hands the kernel a device tree blob (a compiled .dtb) — a data structure saying "there's a UART at this memory address, an SD controller at that one, this GPIO drives the LED," etc. Without the *exact right* DTB for your board revision, the kernel boots but can't see most of the hardware.
  • Root filesystem — once the kernel can talk to storage, it mounts the root filesystem (rootfs) — the actual Linux distribution's files.
  • init (PID 1) — the kernel starts exactly one userspace program as process ID 1. Everything else on the system is, directly or indirectly, its child. This is what actually brings up services, networking, and eventually a shell.

3. The Jetson TX2's specific boot chain

The TX2 fills in that generic chain with concrete pieces, and we can point at the exact lines in sources/meta-tegra/conf/machine/jetson-tx2.conf that configure each one:

SoC BootROM
→
U-Boot (p2771-0000-500_defconfig)
→
Image (kernel)
→
tegra186-quill-...dtb
→
eMMC rootfs
→
init
sources/meta-tegra/conf/machine/jetson-tx2.conf
KERNEL_DEVICETREE ?= ".../tegra186-quill-p3310-1000-c03-00-base.dtb"
UBOOT_MACHINE = "p2771-0000-500_defconfig"
EMMC_SIZE ?= "31276924928"        # ~29 GiB — the board's onboard eMMC storage
BOOTPART_SIZE ?= "8388608"        # size reserved for the boot partition
ROOTFSPART_SIZE ?= "30064771072"  # size reserved for the root filesystem
ODMDATA ?= "0x1090000"            # board strapping/config word the BootROM reads
  • The SoC's BootROM is unchangeable silicon logic. On power-up (or when you force it via the recovery button) it reads ODMDATA-style configuration and loads the first-stage bootloader from eMMC.
  • U-Boot, built using the p2771-0000-500_defconfig defconfig specific to the TX2 devkit carrier board, loads the kernel image and the matching device tree blob.
  • The kernel (KERNEL_IMAGETYPE = "Image", the standard uncompressed ARM64 kernel format) boots using exactly the device tree named above — this is a real file, compiled from NVIDIA's Tegra186 device tree sources, describing this specific module/carrier combination (the quill compute module on the p3310-1000-c03 devkit carrier board).
  • The kernel then mounts the root filesystem partition sized by ROOTFSPART_SIZE out of that same eMMC, and starts init.

4. Why this project uses 2018-era software — a choice, not a ceiling

Important, and specific to this board Everything in this project uses software from 2018. For the TX1 that used to be this board's hard ceiling; for the TX2, it's a deliberate choice to stay on the branch already checked out here, not something the hardware forces on us. Worth being precise about the difference.

NVIDIA doesn't upstream full support for Tegra chips into the mainline Linux kernel. Instead they ship L4T (Linux for Tegra): a patched kernel plus closed-source GPU/ISP firmware and userspace libraries, versioned alongside their "JetPack" SDK releases. Each L4T release supports a specific, fixed list of boards.

The TX1 and TX2 both launched under L4T R28.3 (JetPack 3.3) — that's why sources/meta-tegra/conf/machine/ has both a jetson-tx1.conf and a jetson-tx2.conf side by side on the same branch. But their support lifespans then diverged sharply: NVIDIA dropped the TX1 after R28.3, while the TX2 kept receiving L4T updates for years afterward — R32.x (JetPack 4.x) and beyond. So unlike the TX1 project this started as, targeting the TX2 does not require 2018-era software at all.

meta-tegra (the community BSP layer we're using — more on it in Section 7) mirrors NVIDIA's own version matrix branch-for-branch, which makes the TX2's longer support tail visible directly in its branch list:

$ git ls-remote --heads https://github.com/OE4T/meta-tegra.git (excerpt)
thud-l4t-r28.3        ← contains conf/machine/jetson-tx2.conf — what we use
kirkstone-l4t-r32.7.x ← TX2 / Xavier / Nano supported here too, no TX1
master-l4t-r38.x      ← Orin-generation only, no TX1 or TX2

So why stay on thud-l4t-r28.3 for a TX2 build? Purely because that's the branch already checked out in sources/meta-tegra, and re-pinning to kirkstone-l4t-r32.7.x would mean a much bigger change than swapping MACHINE — a different Poky release, a different required host/Docker environment, and a different toolchain, none of which this session touched. The LAYERSERIES_COMPAT_tegra = "thud" declaration in this branch's conf/layer.conf still locks us to Poky's thud branch (Yocto Project 2.6, late 2018) exactly as it did for the TX1 — that mechanical constraint hasn't changed. What's changed is why we accept it: for the TX1 it was the only branch with any support at all; for the TX2 it's simply the one already set up, with a newer option available later if this project ever outgrows R28.3.

5. What the Yocto Project actually is

It's easy to assume "Yocto" is a Linux distribution you download, like Ubuntu. It's the opposite: Yocto is a build system that compiles a custom Linux distribution from source, tailored to exactly the hardware and software you specify. Downloading Ubuntu gives you someone else's finished decisions about what's installed; Yocto makes you (mostly) make those decisions yourself, then builds the result.

It's really two things working together:

  • BitBake — the task-execution engine. Conceptually similar to make, but instead of building one program, it parses thousands of small recipe files, builds a dependency graph across all of them, and executes each one's build steps (fetch, compile, install, package, ...) in the right order, in parallel where possible.
  • OpenEmbedded-Core — the actual metadata: thousands of recipes that know how to fetch and cross-compile everything from the C library up, plus the classes and conventions that make them composable.

Poky, which we clone in this project, is the reference combination of BitBake + OpenEmbedded-Core + a minimal default distro policy, maintained together by the Yocto Project so the two always stay version-matched.

This is why an embedded project uses Yocto instead of "installing Ubuntu on an SD card": you get a rootfs containing precisely the packages you chose, cross-compiled for the target CPU, with a fully auditable build recipe for every byte in the image — valuable when your device has 4–16 GB of storage and needs to boot in seconds, not minutes.

6. Core vocabulary, mapped to real files

Rather than define these abstractly, here's each term next to the actual file in this project that demonstrates it.

Recipe (.bb)
Instructions for building one piece of software: where to fetch it, how to configure/compile/install it. Example: sources/meta-tegra/recipes-bsp/tegra-binaries/tegra-binaries_28.3.0.bb downloads NVIDIA's redistributable L4T binaries.
Layer
A directory tree of recipes and configuration, identified by a conf/layer.conf file. Layers stack by priority — sources/meta-tegra/ and sources/meta-openembedded/meta-oe/ are both layers we added on top of Poky's built-in ones.
BBLAYERS
The variable listing which layers BitBake actually loads, set in build/conf/bblayers.conf — shown in full in Section 7 below.
Machine configuration
sources/meta-tegra/conf/machine/jetson-tx2.conf — defines the target hardware: CPU architecture, bootloader, kernel device tree, storage partition sizes. Selected by setting MACHINE = "jetson-tx2" in local.conf.
Distro configuration
Policy that's independent of hardware — which init system, C library, package format. We kept Poky's default (DISTRO ?= "poky" in local.conf), since "minimal" doesn't require a custom distro policy on top of a custom machine.
Class (.bbclass)
Reusable behavior mixed into recipes — similar to a mixin. Example: sources/meta-tegra/classes/image_types_tegra.bbclass defines the tegraflash image type used in Section 10.
Task
Recipes are broken into staged steps BitBake schedules across the whole dependency graph: do_fetch → do_unpack → do_patch → do_configure → do_compile → do_install → do_package. Detailed in Section 8.
Image recipe
A special recipe that doesn't build one program — it lists which packages to install into a root filesystem. Our target, core-image-minimal, lives in sources/poky/meta/recipes-core/images/core-image-minimal.bb and is Poky's smallest sensible rootfs: just enough to boot and get a shell.
sstate-cache (shared state cache)
Like ccache, but for entire task outputs rather than just compiler objects. Once a task's output is built for a given set of inputs, it's cached under sstate-cache/ (we pointed SSTATE_DIR there) so future builds reuse it instead of recompiling identical work.

7. BSP layers, and why meta-tegra exists

A Board Support Package (BSP) layer adds everything generic OpenEmbedded-Core has no way of knowing about a specific board: the bootloader recipe and its board-specific config, a kernel built with the right defconfig and device tree, any vendor-proprietary firmware blobs, and the machine .conf file tying it together. meta-tegra is exactly that for NVIDIA Tegra boards. Concretely, for the TX2, it provides:

  • A U-Boot recipe built with the p2771-0000-500_defconfig defconfig
  • A Linux kernel recipe with Tegra186 support and the matching device tree source
  • tegra-binaries — fetches NVIDIA's redistributable L4T binary blobs (GPU/ISP firmware, CBoot, flashing tools) that aren't open source and can't be built from scratch
  • tegra-configs-nvstartup / tegra-configs-udev / tegra-nvpmodel — board-specific startup, device-naming, and power-mode configuration, listed as required dependencies directly in tegra186.inc: MACHINE_EXTRA_RDEPENDS = "tegra-nvpmodel tegra-configs-nvstartup tegra-configs-udev" (the TX1's tegra210.inc pulls in the same two configs but has no tegra-nvpmodel entry — that package is TX2/Xavier-and-later, where NVIDIA's power/clock modeling tool actually applies)

Here is the actual layer stack this project ends up with, from build/conf/bblayers.conf, lowest-priority (generic) at the bottom of the visual stack to most-specific (our board) toward the top:

meta-tegraTX2 board support
meta-openembedded/meta-oeextra common recipes
poky/meta-yocto-bspreference/QEMU machines (unused here)
poky/meta-pokydefault distro policy
poky/metaOpenEmbedded-Core — the generic base

8. What happens when you run bitbake core-image-minimal

This hasn't been run in full yet in this project (see the callout at the end of this section), but here's exactly what it will do once started, stage by stage, per recipe, across the whole dependency graph:

  1. Parse — every recipe in every layer in BBLAYERS is parsed and a dependency graph is built. I validated this step already: 1532 .bb files, 2172 targets, 0 errors for this exact layer/machine combination.
  2. do_fetch — downloads each recipe's source (tarball or git repo) into DL_DIR (downloads/ in this project — shared across rebuilds, safe to keep forever).
  3. do_unpack — extracts the fetched source into a per-recipe working directory under TMPDIR.
  4. do_patch — applies any patches the recipe specifies, on top of the unpacked pristine source.
  5. do_configure — runs the project's own configure step (autotools, cmake, kernel oldconfig, ...), targeting the TX2's aarch64 architecture via a cross-compilation toolchain BitBake builds for itself first.
  6. do_compile — actually compiles it, cross-compiled for ARM64, never running any of this code on your x86_64 build machine.
  7. do_install — stages the compiled output into a temporary "destination directory," mimicking a real root filesystem layout.
  8. do_package — splits that staged output into one or more installable binary packages (.rpm here, per PACKAGE_CLASSES in local.conf).
  9. do_rootfs — once every package core-image-minimal needs exists, they're all installed together into an actual root filesystem tree.
  10. do_image_* — the rootfs tree is packaged into final artifacts under build/tmp/deploy/images/jetson-tx2/ — for us, that includes a tegraflash.zip (Section 10).
Scale, for context A first build compiles roughly 1,500 recipes from source — most of userspace Linux, plus a cross-toolchain, plus the kernel — which typically means tens of gigabytes downloaded and several hours of compilation even on a fast multi-core machine. Every subsequent build reuses sstate-cache and is dramatically faster, which is why that cache lives outside build/ and survives you deleting and recreating the build directory.
Not run yet, by design This session set up and validated the configuration (layers resolve, 0 parse errors, MACHINE and IMAGE_FSTYPES both confirmed correct via bitbake -e) but deliberately stopped short of running the real multi-hour build. When you're ready: ./docker/build.sh, then inside the container source sources/poky/oe-init-build-env build && bitbake core-image-minimal.

9. Why the build runs inside Docker

Yocto 2.6 ("thud") is 2018-era software, and BitBake is sensitive to exactly what's on the build host: its Python version, its C library, even which packages are present. This machine runs Ubuntu 24.04 (Python 3.12, glibc 2.39, gcc 13) — new enough that building "thud" directly on it would hit real incompatibilities.

Rather than fight that by patching old BitBake to understand a much newer host, this project builds inside a Docker container running Ubuntu 18.04 — the environment "thud" actually expects — defined once in docker/Dockerfile and never drifting, regardless of what's installed on your laptop.

This wasn't a hypothetical concern — it's exactly what happened while setting this project up. The Yocto 2.6 manual's documented package list for Ubuntu doesn't happen to mention the file utility, but BitBake's own startup sanity-check (HOSTTOOLS) refuses to run without it:

first run inside the freshly-built container
ERROR: The following required tools (as specified by HOSTTOOLS) appear to be
unavailable in PATH, please install them in order to proceed:
  file

That's a real, concrete example of the class of problem strict environment-pinning exists to solve: a one-line fix in docker/Dockerfile (apt-get install ... file ...) and it never has to be diagnosed again, by anyone who builds this project, on any host.

docker/build.sh wraps the two commands you'd otherwise run by hand: it builds the image (fast, cached after the first time) and drops you into a shell with sources/, build/, downloads/, and sstate-cache/ bind-mounted from this project directory, so nothing produced inside the container is lost when it exits.

10. From build output to a booting board

Once bitbake core-image-minimal finishes, the artifacts land in build/tmp/deploy/images/jetson-tx2/. We specifically configured local.conf to produce a flashable package, using meta-tegra's tegraflash image type:

build/conf/local.conf
IMAGE_CLASSES += "image_types_tegra"
IMAGE_FSTYPES += "tegraflash"
Verified, not assumed IMAGE_CLASSES has to be set explicitly — meta-tegra doesn't inherit its own flashing class by default. Leaving it out was actually tried first in this session and broke parsing for every image recipe in the build (No IMAGE_CMD defined for IMAGE_FSTYPES entry 'tegraflash') — adding the class line fixed it, confirmed with a clean bitbake -p afterward.

That combination produces core-image-minimal-jetson-tx2.tegraflash.zip, containing the kernel, the device tree, the rootfs image, and a generated doflash.sh script that wraps NVIDIA's own tegraflash.py tool.

To actually get that onto your board:

  1. Put the TX2 into Force Recovery Mode — with the board powered off, hold the RECOVERY button, tap RESET (or apply power) while still holding it, then release after a couple seconds. In this mode the SoC's BootROM itself exposes a USB device to your host — no working bootloader on the board is required, which is also how you recover a bricked one.
  2. Connect the TX2 to your build machine via USB, and confirm the host sees it (typically lsusb shows an NVIDIA device in APX mode).
  3. Unzip and run the flash script from inside the container, as root/with the right USB permissions, from the extracted tegraflash.zip: ./doflash.sh. It calls tegraflash.py --bl cboot.bin --bct ... --cmd "flash;reboot" ..., which writes every partition and reboots the board straight into the new image.

None of this was run in this session — it requires the physical board connected over USB, which only you can do — but the artifact that makes it possible is now configured correctly to be produced by the build.
