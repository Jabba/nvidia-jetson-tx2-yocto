§ How layers compose, briefly

Every layer is just a directory with a conf/layer.conf in it. That file registers the layer under a collection name (BBFILE_COLLECTIONS), tells BitBake where to find its recipes (BBFILES), declares a priority (BBFILE_PRIORITY_<collection>), and can declare dependencies on other collections (LAYERDEPENDS_<collection>). None of that does anything on its own — a layer only actually gets used once its path is listed in BBLAYERS inside build/conf/bblayers.conf, which is this project's actual opt-in list:

build/conf-templates/bblayers.conf
BBLAYERS ?= " \
  /work/sources/poky/meta \
  /work/sources/poky/meta-poky \
  /work/sources/poky/meta-yocto-bsp \
  /work/sources/meta-openembedded/meta-oe \
  /work/sources/meta-tegra \
  "

That's the entire universe this build draws from: five layers, in that order. Everything below is one of those five, in the same order they're listed above.

1. meta — OpenEmbedded-Core

sources/poky/meta collection: core

Priority: 5 Depends on: nothing (the root) Series: thud

The foundation every other layer here builds on. This is not Tegra- or embedded-specific at all — it's the generic core of the whole Yocto Project: the base bitbake.conf, the C library and toolchain recipes (glibc, gcc, binutils), core userspace (busybox, systemd/sysvinit, udev), the packaging classes (package_rpm.bbclass, package_ipk.bbclass...), and the machine/arch tune files every other layer's machine .conf ultimately requires.

Its conf/layer.conf is the one every other layer here implicitly needs, because every other layer's LAYERDEPENDS_* points back at core:

sources/poky/meta/conf/layer.conf (excerpt)
BBFILE_COLLECTIONS += "core"
BBFILE_PRIORITY_core = "5"
LAYERSERIES_CORENAMES = "thud"
LAYERSERIES_COMPAT_core = "thud"
COREBASE = '${@os.path.normpath("${LAYERDIR}/../")}'

COREBASE is worth noticing: it's computed as "one directory up from meta/" — i.e. sources/poky. Every other layer's own layer.conf and machine includes ultimately resolve paths relative to this. It's also the layer that defines LAYERSERIES_COMPAT_core = "thud", the exact string every other layer here has to match in its own LAYERSERIES_COMPAT_* or BitBake refuses to load it at all — this is the mechanical enforcement behind the "everything is pinned to 2018" constraint described in the project overview.

Recipe categories under meta/recipes-* give a sense of scope — this one layer alone covers recipes-core (init, C library, base utilities), recipes-devtools (the entire cross-toolchain: gcc, binutils, cmake, python), recipes-kernel, recipes-bsp, recipes-connectivity, recipes-graphics, recipes-multimedia, recipes-extended, recipes-gnome, recipes-rt, recipes-sato, and recipes-support. Roughly a thousand of the ~1,500 recipes this build parses come from here alone.

2. meta-poky — the Poky distro policy

sources/poky/meta-poky collection: yocto

Priority: 5 Depends on: core

Much smaller and much more specific: it doesn't add hardware support or a large recipe set, it adds distro policy — the answer to "given the generic building blocks in core, what does a coherent, opinionated Linux distribution actually look like." This is what DISTRO = "poky" in local.conf actually selects.

sources/poky/meta-poky/conf/layer.conf (excerpt)
BBFILE_COLLECTIONS += "yocto"
BBFILE_PRIORITY_yocto = "5"
LAYERDEPENDS_yocto = "core"
REQUIRED_POKY_BBLAYERS_CONF_VERSION = "2"

Concretely it contributes very little in recipe count — just three package customizations under recipes-core/ (busybox, psplash the boot splash, and a small tiny-init recipe) — plus the actual conf/distro/poky.conf policy file that sets things like the default package format preference and version/tclibc defaults referenced from local.conf. REQUIRED_POKY_BBLAYERS_CONF_VERSION is also the exact mechanism behind the POKY_BBLAYERS_CONF_VERSION = "2" line at the top of this project's own bblayers.conf — if those two didn't match, BitBake would refuse to start, telling you your bblayers.conf is out of date for this Poky release.

3. meta-yocto-bsp — reference machines

sources/poky/meta-yocto-bsp collection: yoctobsp

Priority: 5 Depends on: implicitly core

Ships with Poky as the set of "reference hardware" machine definitions the Yocto Project itself supports and tests against — QEMU targets and a handful of real reference boards.

Its conf/machine/ directory is the tell: beaglebone-yocto.conf, edgerouter.conf, genericx86.conf, genericx86-64.conf, mpc8315e-rdb.conf. None of these is jetson-tx2 — this layer contributes zero machine support to this specific build. It's loaded purely because it's part of Poky's default bblayers.conf template and doing no harm sitting there at the same priority (5) as everything else non-Tegra; MACHINE = "jetson-tx2" in local.conf simply never matches anything this layer defines, so none of its recipes or machine .conf logic is ever selected. It's listed here for completeness because it genuinely is one of the five loaded layers, not because it does anything for the TX2.

4. meta-openembedded/meta-oe

sources/meta-openembedded/meta-oe collection: openembedded-layer

Priority: 6 Depends on: core

The community's general-purpose recipe layer: thousands of additional packages that are broadly useful but don't belong in OpenEmbedded-Core because they're not needed to build a minimal system. meta-openembedded upstream is actually a bundle of many sub-layers (meta-oe, meta-networking, meta-python, meta-filesystems, ...); this project only loads meta-oe itself, the largest and most general of the set.

sources/meta-openembedded/meta-oe/conf/layer.conf (excerpt)
BBFILE_COLLECTIONS += "openembedded-layer"
BBFILE_PRIORITY_openembedded-layer = "6"
LAYERDEPENDS_openembedded-layer = "core"
LICENSE_PATH += "${LAYERDIR}/licenses"

Note the priority: 6, higher than every other layer in this stack (all at 5). Priority only matters when two layers ship a recipe with the identical name/version — the higher-priority one wins. So meta-oe is deliberately positioned to be able to override an OpenEmbedded-Core recipe if it ever needs to, without that override silently losing to core. It doesn't currently need to for anything this build uses — but see §7 below for how meta-tegra reaches into this layer's content a different way.

Recipe categories here are broad and mostly generic (recipes-connectivity, recipes-crypto, recipes-benchmark, recipes-navigation, recipes-shells, and so on) — none of it TX2-specific. In this project it's present mainly as a dependency source: several packages meta-tegra's own recipes pull in (for example multimedia/codec support packages referenced by the GStreamer/OMX Tegra bindings) live here rather than in core.

5. meta-tegra — the TX2 BSP

sources/meta-tegra collection: tegra

Priority: 5 Depends on: core Branch: thud-l4t-r28.3

The reason this project exists: the actual Board Support Package for NVIDIA Tegra hardware, maintained by the OE4T community project. Every piece of TX2-specific knowledge — bootloader, kernel, device tree, closed-source GPU/ISP firmware, partition layout — lives here. Nothing above this layer knows the TX2 exists; everything below it is generic enough to not need to.

What it actually ships, recipe by recipe

recipes-bsp/tegra-binaries/tegra-nvpmodel_28.3.0.bb NVIDIA's nvpmodel power/clock-mode management tool and its tegra186-specific init/service files — pulled in via MACHINE_EXTRA_RDEPENDS in tegra186.inc only; the TX1's tegra210.inc never depends on this package.
recipes-devtools/{cuda,cudnn,cmake,visionworks,gie} NVIDIA's CUDA 9.0 toolkit and related GPU-compute libraries (cuDNN, TensorRT/"gie", VisionWorks) as native/target recipes — not installed by core-image-minimal, but available if a fuller image ever pulls them in. For this board, CUDA_NVCC_ARCH_FLAGS targets compute_62/sm_62 (the TX2's Pascal GPU), not the TX1's compute_53/sm_53 (Maxwell).
classes/image_types_tegra.bbclass Defines the tegraflash image type this project's local.conf opts into via IMAGE_FSTYPES — the class that produces the final doflash.sh + tegraflash.zip flashing bundle.
classes/cuda.bbclass Shared logic for locating the CUDA toolchain and setting GPU architecture flags (CUDA_NVCC_ARCH_FLAGS), consumed by the devtools recipes above.

The machine-config include chain

conf/machine/jetson-tx2.conf is deliberately thin — almost everything it needs is pulled in via a chain of shared .inc files, so the TX1, TX2, and TK1 machine definitions in this same layer share as much as possible:

jetson-tx2.conf
requires
tegra186.inc
requires
tegra-common.inc

tegra186.inc (named for the TX2's Tegra186/"Parker" SoC family) is where the concrete package pins live — this checkout of meta-tegra only defines one Tegra186-family board (the TX2 itself; no Xavier config exists in this branch's conf/machine/), but the include is still kept separate from the machine .conf for the same reason tegra210.inc is: it's the natural place a second Tegra186 board would plug into later. This is the actual source of facts stated elsewhere in this project:

sources/meta-tegra/conf/machine/include/tegra186.inc (excerpt)
SOC_FAMILY = "tegra186"
KERNEL_IMAGETYPE = "Image"
MACHINE_ESSENTIAL_EXTRA_RDEPENDS = "tegra-firmware kernel-devicetree kernel-image"
MACHINE_EXTRA_RDEPENDS = "tegra-nvpmodel tegra-configs-nvstartup tegra-configs-udev"
INITRAMFS_IMAGE ?= "tegra186-minimal-initramfs"
SERIAL_CONSOLE = "115200 ttyS0"
NVIDIA_CHIP = "0x18"
CUDA_VERSION ?= "9.0"
CUDA_NVCC_ARCH_FLAGS ?= "--gpu-architecture=compute_62 --gpu-code=sm_62"
PREFERRED_PROVIDER_virtual/kernel ?= "linux-tegra"      # from tegra-common.inc
PREFERRED_PROVIDER_u-boot ?= "u-boot-tegra"              # from tegra-common.inc

Diffing this against the TX1's tegra210.inc is a good way to see exactly how much a Tegra machine include actually varies board-to-board: SOC_FAMILY, NVIDIA_CHIP, the initramfs image name, and the CUDA architecture flags all change; MACHINE_EXTRA_RDEPENDS gains tegra-nvpmodel; but MACHINE_ESSENTIAL_EXTRA_RDEPENDS, SERIAL_CONSOLE, and every PREFERRED_PROVIDER_* line are identical, because those come from the shared tegra-common.inc both includes pull in beneath them.

PREFERRED_PROVIDER_virtual/kernel is the mechanism that resolves "the kernel" (a generic concept every image recipe depends on via virtual/kernel) to this specific layer's linux-tegra recipe instead of, say, OpenEmbedded-Core's generic linux-yocto. Same pattern for the bootloader via virtual/bootloader → u-boot-tegra. This is how a BSP layer redirects generic build targets toward board-specific implementations without every image recipe needing to know the board exists.

Reaching into another layer: external/

One more mechanism is worth calling out because it's easy to miss: meta-tegra's own conf/layer.conf contains logic that scans an external/ subdirectory for folders matching other loaded layers' collection names, and if found, adds their recipes/bbappends to BBFILES too:

sources/meta-tegra/conf/layer.conf (excerpt)
BBFILES += "${@' '.join('${LAYERDIR}/external/%s/recipes*/*/*.bb' % layer \
    for layer in BBFILE_COLLECTIONS.split() if os.path.exists(os.path.join('${LAYERDIR}','external',layer)))}"

Concretely: sources/meta-tegra/external/openembedded-layer/ exists, and openembedded-layer is exactly meta-oe's collection name from §4 above. Inside it sits recipes-support/opencv/opencv_3.4.3.bbappend — a Tegra-specific patch (0001-samples-eliminate-cvconfig.h-usage.patch) applied on top of meta-oe's OpenCV recipe. This lets meta-tegra carry board-specific patches for another layer's package without needing write access to that layer, without a priority fight, and without that bbappend being visible unless both layers are actually loaded together — exactly this project's situation.

§ Priority, collisions, and load order

Restating the actual numbers for this build, since "priority" is frequently misunderstood as "load order" (it isn't — BBFILES parsing order and priority are separate concerns; priority only decides collisions):

meta-tegrapriority 5 — collection tegra
meta-openembedded/meta-oepriority 6 — collection openembedded-layer
poky/meta-yocto-bsppriority 5 — collection yoctobsp
poky/meta-pokypriority 5 — collection yocto
poky/metapriority 5 — collection core

Four of the five layers sit at priority 5; only meta-oe is higher, at 6. In practice this build has zero same-name/same-version recipe collisions across layers — bitbake-layers show-layers reports all five loading cleanly, and meta-tegra avoids ever needing to out-prioritize core by using PREFERRED_PROVIDER (a targeted, explicit override) instead of a same-named recipe at higher priority. Priority is the blunt, automatic tool; PREFERRED_PROVIDER and bbappends are the precise ones, and this stack relies almost entirely on the precise ones.

§ The dependency graph between layers

Collapsing every LAYERDEPENDS_* declaration seen above into one picture:

meta (core)

↑ required by all four:

meta-poky
meta-yocto-bsp
meta-oe
meta-tegra

It's flat, not deep: every other layer here depends directly on core and on nothing else in this stack. meta-tegra does not formally depend on meta-oe in layer.conf terms (no LAYERDEPENDS_tegra entry names it) even though, as §5 showed, it reaches into meta-oe's OpenCV recipe via the external/ convention and expects several of its packages to be present at build time. That's a soft, content-level dependency BitBake's layer system doesn't formally track — which is exactly why meta-oe has to be listed in this project's bblayers.conf at all, even though nothing declares it as required.

§ Tracing one setting through all five layers

To make the whole stack concrete at once, here's what actually happens, layer by layer, for a single BitBake variable this project depends on: PREFERRED_PROVIDER_virtual/kernel — "which recipe answers when something asks for 'the kernel'."

  1. meta defines virtual/kernel as a concept every image recipe can depend on, and ships a default generic provider (linux-yocto) that nothing here ends up using.
  2. meta-poky and meta-yocto-bsp don't touch this variable at all for this machine — they're irrelevant to the TX2's kernel choice.
  3. meta-oe also doesn't touch it — it has no kernel recipes of its own.
  4. meta-tegra's tegra-common.inc, pulled in via jetson-tx2.conf → tegra186.inc, sets PREFERRED_PROVIDER_virtual/kernel ?= "linux-tegra" — and because this is the only layer in the whole stack that sets it for this MACHINE, it wins by default, no priority contest needed.

The result: bitbake core-image-minimal resolves virtual/kernel to meta-tegra's linux-tegra_4.4.bb, which builds with the tegra186/defconfig baked into that same layer (via SOC_FAMILY = "tegra186" feeding into the recipe's machine-override file search path). Every other variable this project cares about — the bootloader, the image type, the device tree — resolves the same way: one layer, usually meta-tegra, is the only one with an opinion, so composition reduces to "does every layer parse cleanly," which is exactly what bitbake -p checks.
